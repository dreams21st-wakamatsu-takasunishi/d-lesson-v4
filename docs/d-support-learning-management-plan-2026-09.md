## 1. 統合後の役割

- Dレッスン: 児童ログイン、割り当て課題の表示、練習、途中保存、確認申請、結果・承認反映、子ども向け報酬・演出。
- Dサポート: 児童名簿との対応づけ、学習アカウント管理、実績確認、課題割り当て、取り組み範囲指定、Word確認・承認、記録下書き反映、教材・報酬・運用設定。
- 学習エンジン・課題判定・児童Auth・学習データの保存先は、初期移管ではDレッスン側を維持する。操作画面の移管と、DBの移行を混同しない。
- 管理・承認はDサポートの職員認証を利用する。Dサポートへの児童アカウント作成や、児童端末での職員パスワード入力は教室連携の通常経路に不要とする。
- 学習実績と職員の観察を合わせ、既存の支援経過記録の下書き・保存・確認へつなぐ。Word承認を記録の承認と同一にしない。

## 3. Dサポート側で活かす既存機能

- `ChildrenManager` / `children`: 児童名簿、氏名・生年月日等の編集。名簿から学習アカウントを新規発行するか、既存IDを対応づける。
- `TeamManager` / `RolePermissionManager`: 職員、記録者、端末、管理権限の入口。学習の閲覧・割り当て・承認等の権限を追加する。
- `RecordForm` / `recordSaveWorkflow`: 複数児童の下書き、PC欄、比較保存、版の競合確認。学習結果の再入力を減らす。
- 記録の確認・要修正・印刷: 既存の正式な記録確定手順を維持する。
- お知らせ・アプリ内通知・Web Pushの仕組み: 表示・配信部分を再利用できる。ただし現在はお知らせ等を対象としており、Word申請の台帳・担当者限定通知は追加が必要。
- 事業所端末の制約: 学習閲覧・承認・割り当ても同じ制約に合わせる。送迎専用の個人端末に児童の学習情報を自動公開しない。

学校台帳は通学先の学校であり、Dレッスンの校舎と同じデータではない。校舎はDサポートの事業所に明示的に対応づける。

## 4. 統合・廃止・維持の判断

### 移管先が完成してから廃止する入口

- Dレッスンの教室運用向け管理者・先生メニューと、両者に重複する一覧・名簿・印刷・報酬操作。
- 教室の児童端末で先生がメール・パスワードを入力するWord承認ダイアログ。
- 同じ児童の業務氏名・生年月日を両アプリで独立編集する操作。Dサポートを編集元にする。ただしニックネームは別設定。
- 通常業務でのAuth User ID入力・SQLコピー。既存アカウントの救済・初期設定は権限制限付きの復旧手順に残す。
- 「未クリア課題を使わせる」目的でクリア済み進捗を書き換える全開放操作。利用許可・前提条件の個別免除へ置換する。
- 端末内だけの管理ログを正式監査として扱う運用。既存ログは移行資料として保持し、サーバー側の監査へ移行する。

### 機能は残すが通常画面から分けるもの

- 進捗訂正・リセット・永久削除・大規模復元: 管理者限定、対象確認・理由・変更前後・監査・必要に応じた再認証。
- リズム譜面・テーマ・演出の編集: 教材編集権限を持つ職員向け。日々の記録操作には出さない。
- 公開ユーザーの削除・ランキングNGワード等: 「Dレッスン全体管理」の専用権限。事業所管理者へ自動付与しない。

### Dレッスンに残すもの

- 児童の学習、結果表示、課題への移動、マイページ、子ども向け演出・きせかえ・ガチャ・賞状・ランキング。
- 児童Auth・公開登録・ゲスト。教室に紐づかない一般公開ユーザーはDサポート名簿へ自動登録しない。
- 学習判定・ステージ前提条件・報酬判定・音声再生等の学習エンジン。
- 移行中の限定復旧入口。一般公開利用者の対応手段が未整備のまま、全管理機能を一律削除しない。

管理用入口をDサポートへ移すことと、アプリ全体の運営権限を全事業所へ渡すことは別。Dサポートの `admin` だけを根拠にDレッスン全児童への操作を許可しない。

## 6. 新規追加: 課題割り当てと取り組み範囲

### 3つの設定を分ける

| 設定 | 意味 | 例 |
| --- | --- | --- |
| 今日・今週の課題 | 優先して取り組む課題。未着手・途中・達成を管理 | マウスの指定2ステージを各1回 |
| 利用できる範囲 | 起動可能な分野・ステージ・難易度・自由時間等 | キーボードの指定範囲内、ビジョンはeasyのみ |
| おすすめ順 | 次の提案と教材テンプレートの順序 | マウス -> ABC導入 -> キーボード |

現行の標準ルートは6分野の並べ替えが中心で、省略した分野も末尾に補われる。文章課題には表示 / 非表示・対象グループがあるが、全練習を横断する個人別の範囲指定はない。

### 最初に追加する項目

- 対象: 事業所・グループ・児童。適用範囲は内部IDで確定し、同じグループ名の別事業所を巻き込まない。
- 課題: 安定したステージID・教材版、分野、範囲、難易度、必須 / 任意、必要回数。範囲端点は表示文字の単純な辞書順で決めない。
- 期間: 開始日・終了日、当日コマ、繰り返し曜日。期限切れ・欠席日の扱いを別にする。
- 達成: 今回の割り当て後に実施するか、既存クリアも認めるかを指定。過去の最高記録だけで今日の課題を達成にしない。
- モード: 「おすすめ中心」「指定課題中心」「指定範囲のみ」。初期導入はおすすめ中心から始め、制限は職員が明示設定する。
- 復習: 許可範囲内のクリア済み課題の再実施可否。自由時間・ミニゲーム・リズム・外部サイトは別々に利用可否を指定する。
- 適用前確認: 全対象・既存個別設定・前提未達の課題・児童画面のプレビューと、確定後の配信状態。

### 設定の優先順位と矛盾

個人の当日・コマ設定 > 個人の期間設定 > グループ設定 > 事業所既定、として有効な設定を1つ確定する。同じ優先度の重複期間は保存時に拒否または職員が解消し、画面に採用元を表示する。アプリ全体の停止・安全制約は個別設定で解除しない。

前提未達の課題は理由と代替を提示する。配慮による前提免除は独立した許可・理由・期限を保存し、実際にクリアした進捗にはしない。全開放で既存記録をクリア扱いにする方式は採用しない。

### 児童画面への反映

- 最初に「きょうのれんしゅう」を表示し、課題から直接ステージへ移動できる。
- 禁止範囲はメニューだけでなく、おすすめ・再挑戦・別入口・直接起動でも判定する。
- 管理設定は児童が更新できる `user_data` のJSONだけに保存しない。サーバーで管理された版付き設定を参照する。
- 学習開始時に適用版を保持し、途中変更は原則次の課題開始時から適用。緊急停止は別扱いとする。
- 通信失敗では制限を全開放しない。最終確認済み設定の有効期限とオフライン継続条件を設計し、初回未取得の場合は管理対象の課題起動を保留する。
- ブラウザーの表示制御は不正操作に対する完全な防御ではない。申請・報酬・課題達成の確定でもサーバー側の範囲・前提・版を検証する。

初期版の範囲指定は教室児童のみ。公開ユーザー・ゲストへ教室の割り当てや制限を自動適用しない。

## 7. 新規追加: Word確認申請・通知・承認

### 現在との違い

現在は児童画面で一時的な先生クライアントを作り、Dレッスン側の先生Authで `approve-word-stage` を呼ぶ。正式な承認は `lesson_word_approvals` にあり、初回500コイン・同じ課題の重複報酬防止・前提条件確認を行う。申請台帳、未確認一覧、担当職員への通知はない。

新方式では、この承認実績を活かしつつ、承認前の申請とDサポートの職員認証を追加する。Dサポートの職員IDを、既存SQLが期待するDレッスン先生IDとしてそのまま渡しても動作しない。プロジェクトを含む承認者情報と認可契約を追加設計する。

### 操作の流れ

1. 児童が課題・終了ページを確認し、「先生にみてもらう」で申請する。
2. Dレッスン側でログイン本人、課題、前提、連携対象を確認し、申請スナップショットをクラウド保存する。保存成功を確かめて「先生のかくにんまち」と表示する。
3. Dサポートの担当範囲の職員に未確認バッジ・アプリ内通知を出す。Web Pushは許可された端末で任意追加する。
4. 職員が児童・課題・ページ・申請版と実際の成果物を確認する。「承認」「もう一度やってみよう」「対応中」を選べる。
5. 承認操作をサーバーに送り、最新の担当範囲・申請状態・前提・重複報酬を確認してDレッスン側でクリアと報酬を確定する。
6. Dサポートに承認者・日時・反映結果を保存し、Dレッスンへクリア・次の課題・初回報酬を反映する。
7. やり直しの場合は児童に短いコメントを返す。児童が再提出すると新しい版になり、旧版を承認しない。

現行ソースでは申請成果物をDサポートから閲覧する機能は確認できない。ページ数だけで内容を見たことにしない。初期版は現物・児童端末で確認し、ファイル添付は保存先・閲覧権限・容量・形式等を定めて後続追加する。

### 状態と通知

- 申請状態: 下書き / 申請済み / 対応中 / やり直し依頼 / 承認済み / 取消。
- 反映状態: 未処理 / 反映中 / 反映済み / 反映失敗。学習側確定前は「承認処理・反映待ち」であり、クリア済みと表示しない。
- 同一児童・課題・申請版の連打は同じ申請として処理する。修正は版を上げ、旧版は取消・置換扱いにする。
- 複数職員の同時承認は版と状態を条件に処理し、1回だけ確定する。二重報酬を防ぎ、既クリア課題の再申請でも追加500コインを付けない。
- 通知を閉じても申請は消えない。通知失敗は申請保存失敗と区別する。未確認一覧と再取得・再配信が基本経路。
- ロック画面通知には氏名・ページ・成績を載せず、汎用通知から認証済み一覧へ移動させる。広域のお知らせとして全職員へ配信しない。
- 連携解除・転所・退所・権限失効後は、その時点の対象範囲を再確認する。異なる児童や再提出前の版への承認を拒否する。
- 公開の個人利用者は、自動的に事業所の確認一覧へ入れない。未連携時の申請先と案内を別途定める。ゲストはクラウド申請対象外。

### 学習側の競合対策

児童自身が学習JSONを保存する現構造では、遠隔承認直前の古い状態を後で保存する可能性がある。承認台帳・申請版・保護された報酬情報を正とし、保存時に承認済み状態を維持・再構成する処理が必要。更新通知だけでは解決しない。

## 8. 権限・連携・保存の設計条件

### 権限案

既存役職を土台に、次を別権限にする。単純な役職名の対応ではなく、担当事業所・児童と端末条件も確認する。

- 学習実績閲覧・下書き反映。
- 課題割り当て・範囲変更・前提免除。
- Word確認・承認。
- 学習アカウント作成・合言葉再発行。
- 教材作成・報酬付与。
- 進捗訂正・退会・復元。
- Dレッスン全体の公開ユーザー・共通設定管理。

Word承認は担当の一般職員にも付与可能とし、児発管だけへ集中させない案。正式な支援経過記録の承認権限は既存どおり維持する。共有ログイン時も、認証された職員 / 記録者の識別を保証し、自由入力の氏名だけを監査上の実行者にしない。

### データの編集元・アカウント作成

- 業務プロフィールはDサポート、学習進捗・児童AuthはDレッスン、割り当て・範囲設定はDサポートを編集元とする。
- Dサポート名簿の既存児童へ「学習アカウント発行」を追加する。学習IDと児童Auth、連携リンクを一連の処理として管理する。
- 別Supabase間は単一DBトランザクションにならない。作成中 / 完了 / 部分失敗、安定した操作ID、同じ処理の再試行と復旧を用意する。
- 現行の児童追加はデータ保存後にAuth作成するため部分成功があり、一括追加はAuthを作らない。移管時はこれらを成功済みと混同しない。
- 旧一括追加には未指定の生年月日を固定日で補う処理がある。名簿統合にはコピーせず、不明・未入力をそのまま扱い、既存データも確認対象にする。
- 合言葉は既存値を一覧で復元する方式にせず、再発行時のカード表示・印刷を基本とする。カードに職員権限や内部Auth IDを含めない。

### サーバー間連携と障害対応

```text
職員がDサポートで操作
  -> Dサポート側で職員・事業所・端末・児童リンク・操作権限を検証
  -> サーバー間の認証付き操作要求
  -> Dレッスン側で許可事業所・対象児童・操作・版を再検証
  -> 学習側で確定し、操作ID付き結果を返す
  -> Dサポートが結果・監査・反映状態を保存
```

児童JWTで職員操作を通さない。サービス権限の秘密はブラウザーや `VITE_*` に置かない。サーバー間の呼び出しにも対象制限が必要で、接続用の秘密だけを持てば全児童を操作できる設計にしない。重送・片側障害に備え、送信待ち台帳と再試行を持つ。

### 新設データの候補

| 保存対象 | 所有側・責任 |
| --- | --- |
| 事業所・児童リンク | Dサポートで編集、Dレッスン側でも許可範囲を確認 |
| 課題・範囲ポリシー | Dサポートで管理、版付きで学習側へ配信・確認 |
| 割り当て実績 | 学習イベントと課題版を紐づけ、今回の達成を判定 |
| Word申請台帳 | Dレッスン側で保存、Dサポートに担当範囲の確認用データを連携 |
| Word承認の正式台帳 | Dレッスン側で報酬と確定、Dサポートの承認者出典を保持 |
| 操作・配信・反映台帳 | 両側の操作ID・状態・再送・照合を保持 |
| 管理監査 | サーバーで実行者・対象・理由・変更前後・結果を保存 |

現在の学習履歴の300件・180日と、端末内管理ログの200件は連携・監査台帳の代わりにしない。

### 退所・削除・バックアップ

- Dサポートの名簿削除は現状ソフト削除、Dレッスンの削除はAuth・学習データ削除を含む。移管では「連携停止」「教室ログイン停止」「学習データ削除」「名簿非表示」を別操作にする。
- 退所時は原則まず連携・利用を停止する。正式な支援記録は学習アカウント削除に連動削除しない。
- 現行JSONバックアップは `users` と端末内管理ログが中心で、児童Auth・アクセス権・正式Word承認台帳・音声ファイルを含む完全復元ではない。
- 移管後は学習データ・連携ID・ポリシー・申請 / 承認・監査・音声・Authの復元対象を明示し、事業所の復元で公開ユーザーや他事業所を上書きしない。

## 9. 推奨する段階と完了条件

| 段階 | 実装対象 | 確認すること |
| --- | --- | --- |
| 1. 土台 | IDリンク、事業所対応、操作権限、試験アカウント | 誤リンク・他事業所・未連携・公開 / ゲスト・送迎専用端末を適切に拒否 |
| 2. 業務入口 | 本日の学習、児童別実績、出典付き記録下書き反映 | 二重取込なし、コマ割当、観察未入力を補完しない、既存記録ロックを維持 |
| 3. Word申請 | 申請台帳、未確認通知、承認 / やり直し、学習側反映 | 同時承認・再提出・古いJSON保存・通知不許可・反映失敗・再送・権限失効 |
| 4. 学習指定 | 割り当て、範囲・難易度・自由時間、児童の今日の課題 | 旧クリアと当日達成を区別、前提矛盾、優先順位、直接起動、オフライン、版競合 |
| 5. 管理入口移管 | 名簿 / Auth / カード、教材、報酬、詳細レポート、運用設定 | 部分作成失敗、同名・同番号、所属変更、公開と事業所権限の分離 |
| 6. 一本化 | 監査・バックアップ、旧入口の停止 | 復旧手順、正式承認台帳・音声の復元、他事業所に影響なし、停止後も児童学習可能 |

構造化学習イベント・長期保存・再送は、段階2から必要範囲を整え、範囲指定・承認の運用開始までに確定する。全移管完了まで放置しない。

旧画面は移管検証が済んだ機能から、読取専用 / 限定管理 -> 停止の順に切り替える。二重編集期間を短くし、編集元を明示する。疑似OS化、全DB移行、児童・職員Authの一本化、凍結中の支援計画・5領域の再開はこの変更に含めない。

## 10. 引き継ぎに追加する決定事項

1. 各事業所の学習管理責任者と、一般職員に認める割り当て・Word承認・報酬付与範囲。
2. 課題中心か範囲制限中心か、初期既定、自由時間・外部サイトの扱い、前提免除の担当者。
3. 当日課題 / 期間課題の達成条件、既クリア課題の再実施、欠席・期日・複数コマの扱い。
4. Wordで確認する成果物と申請コメント、やり直し・申請取消・承認訂正の運用。添付は初期版に必須としない。
5. 公開ユーザーの管理・承認手段を残す場所と、Dレッスン全体管理者の指定。
6. 名簿・学習アカウント・正式記録の退所、停止、削除、復元、保存期間の切り分け。
7. 旧管理入口の停止条件と、連携障害時の運用・復旧担当者。
