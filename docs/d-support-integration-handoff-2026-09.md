# Dレッスン・Dサポート連携案と開発引き継ぎ

作成日: 2026-09-30

状態: 第1段階の学習管理・ID連携・当日実績閲覧を実装済み。連携用DBとFunctionは配備・架空児童で実接続確認済み。公開フロントエンドと実児童の連携は未公開・未有効化。管理機能の全面移管・Word承認・課題割り当ては後続段階。

更新方針: 管理者・先生の操作入口をDサポートへ集約し、児童別の取り組み範囲指定とWord確認申請を追加する。詳細は [管理機能移管・学習管理の検討案](d-support-learning-management-plan-2026-09.md) を参照する。この資料と異なる点は更新方針・詳細資料を優先する。

## 1. 目的と推奨する形

児童がDレッスンで学習すると、職員がDサポートでその日の取り組みを確認でき、支援経過記録のパソコン欄に反映できるようにする。職員は実際に観察した指使い・姿勢・切り替えなどを選択し、必要な場合だけ短い補足を入力する。

最終形は「Dレッスン: 児童の学習」「Dサポート: 職員の学習管理・記録作成」とする。移管は段階的に実施し、学習実績の連携に続いてWord確認申請・承認、課題割り当て・範囲指定、名簿・教材等の管理入口を整える。児童向け画面と学習機能を活かし、ログインやDBを一度に一本化する必要はない。

### Dレッスンのデータの使い方と限界

- `practiceLogs` は `id / at / category / title / detail / amount / coins` を持つ。既定では最新300件、180日以内に制限される。環境変数で変更可能。
- `at` は主に結果・中断等を記録した時刻。学習開始時刻やコマの開始時刻ではない。記録間の時間差を学習時間として扱わない。
- `amount` は文章形式。キーボードでは入力回数・ミス回数・正確さ、ビジョンでは所要秒数、文章入力では入力文字数・ミス箇所数・スコア等を含むが、種類ごとに形式が異なる。
- `mouseLevel / keyboardSequence / examRecords / textRecords / wordProgress` は進捗・最高記録・直近情報等であり、すべての過去の実施日の結果を復元する台帳ではない。
- 完了以外に、中断、Wordの途中保存・承認、自由時間、ガチャ、ミッション報酬等も履歴に入る。履歴の全行を練習回数として数えない。
- 当日結果、最高記録、初回クリア、既クリア課題の復習、途中保存を区別する。コイン数を達成度の根拠にしない。
- 児童自身が自分の `user_data` を保存する構造。学習アプリの結果と職員の確認済み観察は別の情報として扱う。

### Dサポート側の既存の受け口

- 平日テンプレートには `period1 / period2` の取り組み欄があり、パソコン取り組み内容・左右の指の使用本数・姿勢・自由時間からの切り替えを入力できる。
- パソコン取り組みの詳細に `selections` と `dLessonActivities` がある。現行選択肢はマウス、ビジョン、タイピング、ブラインドタッチ、文章入力、Word。
- 休日テンプレートも学習・パソコンの共通入力部品を利用する。連携結果は日付だけでなく、平日の1・2コマ目、休日の午前・午後のどこへ入れるかを指定する必要がある。
- `SectionFieldAnswer.nestedDetails` は文字列または文字列配列。イベントの構造化データや出典の版管理には専用の保存構造を追加する。
- 既存の保存処理は児童・日付の重複比較とバージョン競合確認を行う。承認済み記録のロック、差戻し、監査、下書きの職員間引き継ぎと整合させる。
- 個人端末は送迎専用。学習情報の閲覧・記録への反映も事業所端末・管理用PCの既存制約に合わせる。
- 個別支援計画・本人支援5領域は現在凍結中。今回の連携を理由に再開を前提にしない。

## 4. 職員の操作イメージ

1. 児童はDレッスンにログインし、通常どおり練習する。
2. Dレッスンのクラウド保存後、Dサポートの「児童・日付」に当日実績の候補を表示する。取得時刻と「取得済み・同期待ち・連携なし・取得失敗」を区別する。
3. 職員が対象のコマを選び、「学習実績を反映」で練習種類と結果を下書きへ入れる。既存の手入力を残した比較表示と取消操作を用意する。
4. 指使い、姿勢、切り替えを既存の選択式入力で記録する。観察していない項目は未確認のままとし、よい状態を自動選択しない。
5. 実績と入力済みの観察から文章案を作る。通常は文字入力なし、特記があるときだけ一言を足すことを目標にする。
6. 職員が確認・保存し、既存の児発管承認・差戻し・PDF出力へ進む。

同じ日に複数回取り組んだ場合はまとめて確認できる。コマの割り当てが不明な実績は「未割り当て」に置き、時刻だけで断定しない。複数児童の一括反映でも、児童・日付・コマ・出典を個別に保持する。

架空データによる文章例:

> マウス練習でM-2をクリアした。文章入力では120文字を入力し、ミスは4箇所であった。

「集中できた」「声掛けで姿勢を直した」等は職員が観察・入力した場合だけ追加する。未入力情報を生成AIや定型文で補完しない。まずは確認できた実績の定型文を作り、既存AIは必要な場合の文章調整に使う。

## 5. 開発の前に決める対応関係

### 児童・校舎の対応

- Dサポートの `(organization_id, child_id)` と、Dレッスンの `(project_ref, data_table, user_data_id)` を管理者が確認して紐づける。
- 名前・生年月日は確認の参考にできるが、自動一致の確定には使わない。Dレッスンではニックネームも使用される。
- 校舎 `campusId` と事業所 `organization_id` の対応も明示する。`main` やグループ名だけで事業所を決めない。
- 初期版は対応済みの教室児童だけを対象とする。公開登録・ゲスト・テスト用データは取り込まない。公開アカウントを教室で使う場合は、管理者による所属確認と連携対象化を別途設計する。
- 重複するリンク、誤対応、転校・退所、複数の学習アカウントがある場合の処理を決める。複数事業所への共有は明示的な許可がある場合だけにする。
- 業務上の児童情報はDサポート、学習の進捗・課題定義はDレッスンを主な編集元とする。

### ログイン・権限の対応

- 職員ログインと児童ログインは初期版で統一しない。メールアドレスが同じという理由で役割を継承しない。
- Dサポートの職員権限とDレッスンの先生の担当範囲を照合し、対応済み児童の学習データだけを連携に許可する。
- 児童はDサポートの名簿、支援記録、職員メモを閲覧・変更できない。
- Wordの学習クリア承認と支援経過記録の承認を別々に保持する。片方の承認をもう片方へ自動転用しない。

## 6. 技術的な連携案

### 最小版: 職員操作に合わせた取得

```text
Dレッスンで学習・クラウド保存
    -> Dサポートの職員が児童・日付を開く
    -> Dサポート側の連携Functionが職員・事業所・端末・リンクを検証
    -> Dレッスン側の出力Functionが許可済み児童の実績だけを返す
    -> Dサポートで出典付きの候補を保存
    -> 職員がコマを指定し、支援記録の下書きへ反映
```

別プロジェクト間の取得はサーバー側で行う。児童のJWTをDサポートの職員認証として扱わない。サーバー間認証もアプリ双方で明示的に検証し、source側に連携許可の確認を置く。強いDB権限のキーはブラウザーへ渡さず、サーバー側で使う場合も対象校舎・児童を制限する。

最小版には「更新」操作、再取得しても重複しない処理、取得失敗の表示を含める。更新日時が新しい行だけ取得する最適化は、同時保存・履歴剪定による取りこぼしを検証してから追加する。

### 次段階: 学習イベントと再送

新しい結果は構造化する。既存 `amount` の文字列解釈は旧データ用の限定対応とし、解釈できない実績は原文を表示して数値を推測しない。

推奨するイベント項目:

| 項目 | 意味 |
| --- | --- |
| `schemaVersion / eventId / sourceRevision` | スキーマの版、安定したイベントID、訂正版の識別 |
| `sourceProject / sourceTable / sourceStudentId / campusId` | 出典と所属。氏名を連携キーにしない |
| `occurredAt / receivedAt / serviceDate` | 実施結果の時刻、受信時刻、日本時間での日付 |
| `sessionId / stageId / stageLabel / category / difficulty` | 練習回、課題と難易度。旧データにない値は空欄 |
| `status` | 完了、中断、途中保存、先生承認等 |
| `metrics` | 入力回数・文字数・ミス回数・ミス箇所数・正確さ・スコア・所要秒数等。単位と算出方法を明示 |
| `durationSeconds` | 計測がある場合のみ。中断・非操作時間の扱いも定義 |
| `rawSummary / verifiedBy / verifiedAt` | 原表示と、職員等の確認がある場合の情報 |

`metrics` は練習種類ごとに適用する。タイピングの打鍵回数、文章入力の文字数、ミスの箇所数を同じ数として合計しない。異なる課題・難易度のスコアを単純比較しない。

追加テーブルの候補（名称は未確定）:

- `lesson_child_links`: 事業所・児童と学習アカウントの対応、所属、確認者、確認日時、解除履歴。
- `lesson_learning_events`: Dサポート側で受け取った学習イベント。`sourceProject + sourceTable + sourceStudentId + eventId + sourceRevision` 等で重送を識別する。
- `record_learning_sources`: 記録の児童・日付・コマ・版と、採用したイベント、採用時点の必要最小限の結果、採用者・採用日時を対応づける。
- Dレッスン側のイベント保存先・送信待ち情報: クラウドで結果保存が成功したことを起点に配送し、失敗時は再送する。ブラウザーを閉じても未送信結果が消えない設計にする。

長期保存は業務に使う実績を対象にする。300件・180日の履歴は長期の連携台帳の代わりにはしない。既存ログの上限を増やすだけでは欠落・再送・版管理を解決できない。

## 7. 記録の扱いで守ること

- 正式な支援記録には採用時点の実績を残す。Dレッスンの最高記録や進捗が後で変わっても、承認済みの過去の記録を書き換えない。
- 同期が来るたびに `support_records` を直接更新しない。候補の更新と、職員が採用して保存する処理を分ける。
- 既存記録がある場合は、Dサポートの比較保存・バージョン競合確認を使う。承認済みの修正は既存の差戻し等の手順に従う。
- 中断を「クリア」にしない。取得できない・実績がないことを「取り組まなかった」「欠席」と決めつけない。
- 児童の参加状況、利用時間、姿勢、左右の使用指、集中、援助の程度、気持ち、声掛けへの反応は学習スコアだけで埋めない。
- 自由時間の開始・終了記録があっても、自分で切り替えたか、声掛けが必要だったかは観察で確かめる。
- ビジョンのレーダー・ランキングから支援上の能力や診断を自動判定しない。初期版の記録には課題・難易度・本人の結果を使う。
- 生年月日、メール、合言葉、全 `user_data`、児童の入力文章全体等を一律に複製しない。業務記録に必要な情報だけを受け渡す。
- 学習アカウントの削除と正式な支援記録の保存は別の処理。連携停止、解除、取り込んだ実績の保存期間、バックアップ、訂正・削除の扱いを事業所運用に合わせて決める。

## 8. 推奨する実装順序

| 段階 | 成果物 | 完了の判断 |
| --- | --- | --- |
| 1. 対応づけ | 校舎・事業所、架空児童のリンク、対象範囲 | 別児童・別事業所への誤対応を拒否できる |
| 2. 小規模の実績連携 | 当日一覧、取得Function、候補表示、既存PC欄への反映 | 1児童を2度取り込んでも重複せず、観察未入力を補完しない |
| 3. 運用評価 | 少人数の教室児童で確認、平日・休日・複数コマの確認 | 入力時間、必要な手直し、同期漏れを実測できる |
| 4. 履歴と自動同期 | 構造化イベント、保存先、再送、出典の版管理 | 学習端末の切断・重送・履歴剪定後も採用した結果を確認できる |
| 5. 管理移管・学習管理 | Word確認申請、課題割り当て、範囲指定、名簿・教材・管理入口の移管 | 詳細資料の段階別検証を実施し、移管済み入口から重複を解消する |

CSVは短期の確認・過去データ移行の補助手段にできる。現行の取り組みCSVには `userId` と `log.id` がないため、そのままでは本人の確定や重複除去のキーにできない。試験導入で使う場合も内部ID・イベントID等を追加し、推測による名寄せをしない。

## 10. 開発者が読む主要ファイル

### Dレッスン

## 11. 別チャットへ渡せる依頼文

> Dレッスンの管理者・先生の操作入口をDサポートへ移管する設計を進めてください。この資料と `docs/d-support-learning-management-plan-2026-09.md`、両アプリの現行ソースを確認してください。Dレッスンは児童の学習、Dサポートは職員の学習管理・支援経過記録の入口とします。最初に校舎・事業所・児童のIDリンクと当日実績の下書き反映を整え、次にWordの「児童が確認申請 -> Dサポートで通知・承認 -> Dレッスンへ反映」、課題割り当て・取り組み範囲指定を設計してください。現在のおすすめ順と利用範囲制限は別物です。許可範囲をクリア済み進捗に書き換えないでください。職員の観察入力、既存の記録承認・競合・端末制約を維持してください。管理機能は移管先を検証するまで削除しないでください。公開・ゲストと教室児童は分離し、事業所管理者へアプリ全体の権限を自動付与しないでください。両Supabase間の操作はサーバー側で認可し、正式な承認履歴・反映失敗・再送・監査を保持してください。
